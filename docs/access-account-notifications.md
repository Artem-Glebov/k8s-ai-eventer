# Access (Login), Account (User Management), and Notifications (Email Alerts)

## What Changed

Three interconnected user-facing features were implemented in one pass, layering on a common foundation — a new `users` table in SQLite:

1. **Access:** The Streamlit UI now requires a login gate. Previously, the UI was publicly accessible on its ClusterIP Service to anything with cluster network access. Now each page calls `require_login()` and users authenticate via bcrypt-hashed passwords stored in the database.

2. **Account:** A new page (`services/ui/pages/3_Account.py`) lets users manage their own profile (display name, email, notification preference) and change their password. Flat access model — every logged-in user can create, edit, and delete other user accounts. The agent enforces a last-user-delete guard (400 status) to prevent locking everyone out.

3. **Notifications:** Watch targets now send email alerts on Critical-status transitions. A debounce hook in the analyzer prevents re-sending while Critical, but fires again on recovery and re-transition ("flap" behavior). SMTP is configurable per-cluster (must point at an external relay; no in-cluster mail server deployed), and disabled by default.

### Implementation

**Foundation (shared by Access, Account, and Notifications):**

- **`services/agent/db.py`:** New `users` table with columns: `id`, `username (unique)`, `display_name`, `email`, `password_hash`, `notify_on_critical (0/1)`, `created_at`. New `notification_state` table (one row per watch target): `target_name (PK)`, `last_status`, `last_notified_at` (only set on a successful email send).
- **`services/agent/db.py` functions:** `upsert_user_password()`, `list_users()`, `get_user()`, `count_users()`, `update_user_profile()`, `update_user_password()`, `delete_user()`, `get_notification_state()`, `set_notification_state()`, `notification_recipients()` (returns a list of emails for users with `notify_on_critical=1`).

**Access (login gate):**

- **`services/ui/auth.py`** (new module, shared by all pages):
  - `fetch_credentials()`: calls `GET /users` on the agent, reshapes the response into `streamlit-authenticator`'s expected format (`{"usernames": {u1: {...password_hash...}, ...}}`).
  - `get_authenticator(force_refresh=False)`: caches the `Authenticate` object in `st.session_state`, skipping a re-fetch on every page rerun; `force_refresh=True` right after Account-page mutations (password/profile changes) so a user's next authentication check sees current data without a fresh browser session.
  - `require_login() -> str`: renders the login form, calls `st.stop()` if not authenticated (preventing further page execution), otherwise renders a logout control in the sidebar and returns the logged-in username.

- **Library choice:** `streamlit-authenticator==0.4.2` (bcrypt-hashed passwords + signed session cookie). Alternatives rejected:
  - Streamlit's native `st.login()` (shipped 1.42.0, GA in 1.45.0) requires Streamlit >=1.42 (this project pins 1.41.1) *and* an external identity provider (Google, Auth0, Keycloak — confirmed via Context7 against the official Streamlit docs). This project has zero external identity provider dependencies today and chose to keep it that way.

- **Credential transport:** Credentials are NOT stored in `streamlit-authenticator`'s usual YAML file. Instead, the agent exposes a `GET /users` endpoint that returns all users (including `password_hash`), and the UI's `fetch_credentials()` reshapes it into the library's expected format on every login-check. Passwords are bcrypt hashes (meant to be disclosure-resistant) and the endpoint returns them for two reasons: (1) `streamlit-authenticator` needs them in its credentials dict to validate the login form, and (2) a second "hash-stripped" endpoint would add code without changing the actual security boundary (the agent API itself has no auth, as noted below).

- **Every page gains one line:** `Targets.py` (now handles both the old Targets page and a new Targets-CRUD page — unchanged name to avoid breaking existing navigation), `pages/1_Chat.py`, and `pages/2_Cluster_Overview.py` each call `require_login()` right after `st.set_page_config()`. Pages inside the `pages/` directory need an explicit `sys.path.insert(0, <parent dir>)` before `from auth import require_login` to reach the top-level module reliably.

- **Access model:** flat, no roles. Every logged-in user has identical effective access to the UI (same as before gating was added).

- **First-user bootstrap:** The Helm chart auto-generates a random initial admin password into a K8s Secret at install time:
  - **`chart/templates/secret-auth.yaml`** uses the idiomatic `lookup` + `helm.sh/resource-policy: keep` pattern. Two keys are generated: `admin-password` (initial credential) and `cookie-key` (session-cookie signing key). Generated once on `helm install`, never regenerated by `helm upgrade` — same idiom Bitnami-style charts use.
  - The agent reads `admin-password` via `ADMIN_BOOTSTRAP_PASSWORD` env var and seeds exactly one admin row on startup via `seed_admin()` in `services/agent/main.py` (mirrors the existing `seed_targets()` pattern). The password is bcrypt-hashed before touching SQLite; nothing plaintext is ever stored.
  - The Streamlit UI container reads `cookie-key` via `AUTH_COOKIE_KEY` env var (used by `streamlit-authenticator`'s `Authenticate()` constructor, which runs client-side in that process).
  - `chart/templates/NOTES.txt` now tells the installer how to retrieve the generated password: `kubectl get secret <release>-ai-eventer-auth -o jsonpath='{.data.admin-password}' | base64 -d`.

- **Agent API remains unauthenticated:** The agent's FastAPI has no auth gate — it remains reachable by anything with cluster network access to its ClusterIP Service, identical to its current trust boundary. Only the human-facing Streamlit UI got a login gate. Locking down the agent API itself is explicitly deferred as a separate, larger effort (would need its own auth scheme independent of browser session cookies, since the UI calls it server-side).

**Account (user and profile management):**

- **`services/ui/pages/3_Account.py`** (new page, follows the expander-based CRUD pattern from `Targets.py`):
  - Helper functions `api_get()`, `api_post()`, `api_put()`, `api_delete()` for safe server-side requests with error handling.
  - **"My profile" section:** edit own `display_name`, `email`, and `notify_on_critical` toggle; separate change-password form with client-side confirm-match check (`new_password != confirm_password` -> error).
  - **"Manage users" section:** table of all users (flattened, not admin-gated); "Add user" form (username, display name, email, password, notify_on_critical toggle); "Remove user" selector for all accounts except the current one.
  - Mutations call `get_authenticator(force_refresh=True)` right after a successful API call so password/profile changes take effect immediately.

- **`services/agent/api.py`** new endpoints:
  - `GET /users` returns all users (including `password_hash`, reshaped by the UI's `fetch_credentials()` for login).
  - `POST /users/{username}` (409 on duplicate) creates a new user with bcrypt-hashed password.
  - `PUT /users/{username}/profile` updates `display_name`, `email`, `notify_on_critical`.
  - `PUT /users/{username}/password` bcrypt-hashes a new password.
  - `DELETE /users/{username}` (404 unknown, 400 if it's the last user) deletes a user. Last-user guard prevents `count_users() <= 1`.

**Notifications (SMTP client for Critical-transition alerts):**

- **Scope:** Per-target watch target Critical transitions only. Cluster-wide/creative-mode sweeps explicitly do NOT trigger notifications in this pass (out of scope). Slack/Telegram explicitly deferred — email only.

- **`services/agent/notify.py`** (new module, following the project's one-module-per-concern convention):
  - `send_critical_alert(smtp_host, smtp_port, smtp_username, smtp_password, smtp_from, smtp_use_tls, recipients, target_name, namespace, selector_kind, selector_name, findings, remediation) -> bool`: Plain SMTP client using Python stdlib `smtplib`/`email.mime` (zero new dependency beyond `bcrypt`, already added for Access). Subject is `"[ai-k8s-eventer] {target_name} is now Critical"`. Body deterministically includes top findings' detail text and the primary remediation. No LLM call — consistent with "facts-then-narrative" philosophy. Send failures are logged and swallowed (never raised), so one bad email can't break an analyzer tick.

- **Debounce/flap logic:** New `_maybe_notify_critical()` hook in `main.py`'s `analyze_one_target()`, called right after status is computed. Semantics:
  - Fires exactly once on a Degraded/Healthy -> Critical transition.
  - Stays silent on every subsequent tick while still Critical.
  - Fires again if status recovers (Degraded/Healthy) and then re-enters Critical (flap).
  - No stored state yet is treated as an implicit "Healthy" baseline, so a target already Critical on its first-ever analysis still notifies immediately — consistent with the project's "never delay showing a real problem" principle applied everywhere.
  - **Critical detail:** `notification_state` is only updated to `last_status="Critical"` and `last_notified_at=<now>` when the email actually sends successfully. If SMTP send fails, the state row is left untouched (or unset), so the next tick still sees an unhandled transition and retries, rather than silently dropping a problem it never successfully reported.

- **Configuration (always external, never in-cluster mail):**
  - `chart/values.yaml` has new `notifications.smtp.*` block: `enabled` (default `false`), `host`, `port` (587), `useTls` (true), `fromAddress`, `existingSecretName` (reference to a user-created Secret with `username` and `password` keys).
  - Agent reads via `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_USE_TLS` env vars (sourced from the Secret in the Helm Deployment spec).
  - Design rationale: SPF/DKIM/reverse-DNS and general deliverability are practically unsolvable for a random in-cluster server, and outbound port 25 is blocked by most providers/home networks anyway. Operators are expected to supply their own relay (corporate Postfix, Gmail, etc.).
  - Credentials never touch `values.yaml` — always from a user-supplied K8s Secret using the `existingSecretName` pattern (same idiom used by most cloud-native charts).

- **SMTP disabled by default:** If `notifications.smtp.enabled: false` (the default), `_maybe_notify_critical()` still runs every analyzer tick and updates `notification_state` (so debounce/flap tracking stays correct for whenever SMTP is later turned on), but never attempts to send.

## Why This Design, and What Was Rejected

**Shared `users` table as the foundation for Access, Account, and Notifications:**
Access and Account were always going to need user accounts (credentials + profile metadata). Notifications need a flag per user (`notify_on_critical`) to select recipients. A single `users` table with `{username, display_name, email, password_hash, notify_on_critical}` satisfies all three without duplication.

**`streamlit-authenticator` over Streamlit native `st.login()`:**
The native method would require upgrading Streamlit to >=1.42 (currently pinned 1.41.1) *and* adding an external identity provider (Google/Auth0/Keycloak), a new infrastructure dependency. `streamlit-authenticator` is lighter-weight, self-contained, and lets this project remain zero-external-identity today if desired.

**Credentials fetched from `/users`, not a static YAML file:**
The library's default is a YAML file on disk (`{"usernames": {...}}` structure). Bridging live from SQLite means user creation/editing in the Account page immediately affects login credentials without file-watcher race conditions or pod restarts.

**Flat access model with last-user-delete guard, not roles:**
Role-based access (admin/viewer) was rejected — every logged-in user gets identical access (same as before gating). The last-user-delete guard (`DELETE` returns 400 if `count_users() <= 1`) prevents the only account from being accidentally deleted and locking everyone out.

**External SMTP relay, no in-cluster mail server:**
An in-cluster mail server (Postfix, etc.) requires SPF/DKIM/reverse-DNS setup, is practically undeliverable for random deployments, and blocks outbound :25 on many networks anyway. The chart never generates credentials — operators supply their own relay.

**Per-target Critical transitions only, cluster-wide explicitly deferred:**
Cluster-wide sweeps are optional ("creative mode") and already higher-cost. Scoping alerts to explicit watch targets keeps the notification feature simple, observable (only targets the user explicitly cares about), and doesn't conflate unrelated Deployments' problems in one email. Creative-mode alerts are a later expansion.

**Debounce on state transition, not a timer:**
A fixed delay (e.g., "don't re-send for 1 hour") would either hide repeated problems or send duplicate emails on long-running Critical states. Transition-based (Critical -> recovered -> Critical fires again) matches the project's semantic: notify on state changes, not time-based intervals.

**State only updated on successful send:**
If SMTP fails, the state row stays untouched so the next tick retries. Silently advancing the state on a failed send would swallow real problems forever if SMTP is misconfigured but the error isn't actively monitored.

## What to Know for Maintenance

- **Agent API has no auth gate.** The login requirement protects only the human-facing Streamlit UI. Any pod/service inside the cluster can call the agent's `/users`, `/targets`, etc. endpoints without authentication. Locking down the agent API itself is explicitly a separate, larger effort (would need its own auth scheme independent of browser session cookies).

- **Cluster-wide Critical transitions don't notify.** Only per-target watch targets (those in the `targets` table) trigger emails on Critical transitions. The optional creative-mode sweep (`run_creative_mode_tick()` in `main.py`) was deliberately left untouched — cluster-wide notifications are a separate future feature.

- **Slack/Telegram not implemented.** `notify.py` currently sends only email. Other channels (Slack, Telegram, PagerDuty, etc.) are explicitly deferred.

- **SMTP can be disabled; debounce state survives.** If `notifications.smtp.enabled: false`, the `_maybe_notify_critical()` hook still runs and updates `notification_state` every analyzer tick, keeping transition tracking correct. When SMTP is later enabled, debounce/flap logic doesn't skip — it fires correctly based on the accumulated state.

- **No alerting on notification failures.** If SMTP is misconfigured, the agent logs the error and continues. No secondary alert (e.g., Slack) fires to notify an operator that email sending is broken. Operators must actively monitor agent logs or the `notification_state` table's `last_notified_at` timestamps to detect a silent failure.

- **Plaintext email only.** The `MIMEText` message has no HTML variant — purely plaintext. A future expansion could add HTML templates, but the current output is readable and copy-paste-friendly for command references (e.g., `kubectl logs <pod> ...` strings in remediation blocks).
