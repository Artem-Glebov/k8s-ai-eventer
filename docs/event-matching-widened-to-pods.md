# Event Matching Widened to Pods

## What Changed

The agent's SQLite `events` table had been storing raw Kubernetes Events, but the code surfacing them for a watch target (`services/agent/db.py`'s `recent_event_summaries` and `events_for_target`) matched events by exact `involved_name == target.selector_name` (the target's Deployment name). This meant only Deployment-level events (e.g. `ScalingReplicaSet`) were visible to the UI/LLM — Pod-level events owned by that Deployment (e.g. `Failed to pull image`, `BackOff`, `SandboxChanged`) were silently invisible, even though `rules.py`'s deterministic checks independently inspected live pod status and caught the same problems differently.

### Implementation

- Added new SQLite table `target_resources(target_name, namespace, resource_name)` in `services/agent/db.py`
- Table is fully replaced (`DELETE` then `INSERT`) on every analyzer tick in `services/agent/main.py`
- Populated from the Deployment's name plus the current list of pod names owned by it
- Pod names come from `services/agent/rules.py`'s `evaluate_target` function, which now returns a dict `{"findings": [...], "pod_names": [...]}` instead of a plain list
  - `evaluate_target` already performs a `core_v1.list_namespaced_pod(...)` call via the Deployment's label selector, so pod lookup is reused
- `recent_event_summaries(target_name, ...)` and `events_for_target(target_name, ...)` now join against `target_resources` instead of filtering `events` directly
  - Query pattern: `JOIN events e ON tr.namespace = e.namespace AND tr.resource_name = e.involved_name` where `tr.target_name = ?`
- `services/agent/api.py`'s `GET /events` endpoint simplified to pass target name directly instead of unpacking namespace/selector_name

## Why This Design, and What Was Rejected

**Pod name resolution timing:**
Pod names churn on every rollout/restart, so they cannot be stored as a static column on the `targets` table — they must be re-resolved live and kept in sync. Doing resolution in the analyzer loop (which already has Kubernetes API clients) keeps `services/agent/api.py` (the FastAPI read layer) stateless — it only reads from SQLite and never needs its own Kubernetes API client.

**Rejected: prefix matching on `involved_name`:**
A `LIKE '<deployment-name>%'` approach was rejected because Kubernetes ReplicaSet and Pod names are generated by appending a hash suffix to the Deployment name. Prefix matching is fragile — a different, unrelated Deployment whose name happens to be a prefix of another Deployment's name would incorrectly match.

**Rejected: live pod resolution in the API endpoint:**
Resolving pod names inside the FastAPI `/events` endpoint at request time was rejected because it would require giving the read-only API layer its own Kubernetes API client and credentials. The current architecture deliberately avoids this (per the project's "Streamlit talks HTTP only" / single-writer-process design principle).

## Verification

Tested end-to-end against a deliberately broken test Deployment named `example-backend` in the `default` namespace (image tag `nginx:does-not-exist-tag`, no resources/probes) on the `ai-eventer` minikube profile. Confirmed:
- `target_resources` was populated with both the Deployment name and the live Pod name
- `GET /events?target=example-backend` returned Pod events (`Scheduled`, `Pulling`, `Failed`, `BackOff`, `SandboxChanged`) in addition to Deployment events (`ScalingReplicaSet`)
- Previously only the Deployment event was visible

The test Deployment was deleted afterward; nothing remains running in the cluster from this test.

## What to Know for Maintenance

`target_resources` tracks only Deployment name + current Pod names — it does not track ReplicaSet names. ReplicaSet-level events (e.g. `SuccessfulCreate`) targeting the ReplicaSet directly will still not match. This was out of scope for this fix and is a natural follow-up if ReplicaSet-level events prove important for advice quality.
